# PTO 执行模型

## 概述

PTO 的执行模型不是“单线程顺序程序”的直接映射，而是把函数、执行域、数据依赖和同步关系共同组织成一个可分析的并发执行模型。PTO 只承诺保持程序的可观察语义，不把某一种具体调度细节写死在 C++/IR 语义里。

## 执行单元层次

### 编译单元

顶层编译单元负责承载函数、符号和顶层属性。C++ 中对应编译单元（源文件/翻译单元）；IR 中对应 `module`。

### 函数单元

函数是最直接的可编译过程体（C++ 中为普通函数，IR 中为 `func.func`），承载：

- 输入参数
- tile / view / pipe / event 对象
- 控制流与顺序结构

### 执行域

很多 PTO 程序并不是在“无差别通用核心”上执行，而是区分不同执行域（如 cube 路径负责矩阵计算、vector 路径负责逐元素与搬运）。

两种接口形态对执行域的处理方式不同：

- **C++ 内建接口**：执行域由编译器根据所用操作自动推断（例如使用 `TMATMUL` 走 cube 路径，使用 `TADD` 走 vector 路径），用户无需显式声明。
- **IR 操作**：执行域需要显式标记，通过 `pto.section.cube` / `pto.section.vector` 或等价的 `kernel_kind` 函数属性进入。

## SPMD 与 MPMD

PTO 支持两种常见的工作映射方式：

- **SPMD**：Single Program, Multiple Data
- **MPMD**：Multiple Program, Multiple Data

这两种方式描述的是“工作如何映射到执行资源”。

### SPMD

在 SPMD 中，所有参与执行的 block 运行同一份 kernel 入口，只是每个 block 根据自己的运行时身份处理不同的数据区域。

这通常表现为：

- 通过 `get_block_idx()`（IR 中为 `pto.get_block_idx`）
- 必要时结合 `get_subblockid()`（IR 中为 `pto.get_subblock_idx`）
- 计算当前 block 负责的 view offset 或 tile offset

例如：

C++ 写法：

```cpp
auto bid = get_block_idx();
auto base = bid * tile_rows;
```

IR 写法：

```mlir
%bid_i64 = pto.get_block_idx
%bid = pto.index_cast %bid_i64 : i64 to index
%base = pto.muli %bid, %tile_rows : index
```

这种方式适合：

- 规则的张量分块
- block 间结构一致的计算
- 大多数矩阵计算、逐元素计算和规则搬运路径

### Subblock 参与

如果一个 block 内还存在更细粒度的执行参与者，那么可以继续结合：

- `get_subblockid()` / `get_subblockdim()`（IR 中为 `pto.get_subblock_idx` / `pto.get_subblock_num`）

构造更细粒度的逻辑执行编号。

这种方式常用于：

- 一个 block 内进一步切分行/列工作
- 区分不同 subblock 所负责的输入子区域
- 计算每个 subblock 对应的本地偏移或 GM 分区

### MPMD

在 MPMD 中，不同执行资源可以在同一整体任务中执行不同的程序阶段。

对 PTO 用户而言，这种模式通常可以理解为：

- 不同 block 负责不同阶段
- 或由宿主侧分别提交多个不同职责的 kernel
- 或在更高层任务组织中，把不同执行阶段分给不同入口函数

MPMD 更适合：

- producer / consumer 分阶段执行
- 明确区分不同计算职责的多阶段程序
- 需要把一个大任务拆成不同 kernel 职责单元的场景

### 如何选择

如果所有 block 只是处理不同数据分片，但执行逻辑相同，应优先采用 SPMD。

如果不同执行单元承担的是不同程序职责，而不是同一程序在不同数据上的重复实例，则更接近 MPMD。

## 两种编程风格

PTO 的执行模型并不强迫所有用户都以同一种方式组织 kernel。对写 PTO ISA 的用户来说，最常见的两种风格是：

### Auto 风格

Auto 风格更强调：

- 先把 tile、view、输入输出关系表达清楚
- 尽量少手写底层地址和同步细节
- 让编译器在布局、地址和同步上承担更多工作

这种风格更适合：

- 刚开始编写 PTO kernel
- 以正确性和可移植性为优先目标
- 希望先稳定表达算法，再逐步细化控制

### Manual 风格

Manual 风格更强调：

- 显式控制 tile 的放置和局部地址
- 显式控制事件、同步和执行顺序
- 明确指定哪些资源要复用、哪些边界不能交给编译器推断

这种风格更适合：

- 关键路径性能调优
- 需要稳定控制地址与同步细节的 kernel
- 需要与特定执行结构严格对齐的程序

### 两种风格与执行模型的关系

这两种风格并不是两套不同语言，而是同一执行模型下的两种使用方式：

- Auto 风格更多依赖编译器补全执行细节
- Manual 风格更多由用户自己把执行细节写入程序

无论采用哪种风格，最终都必须满足：

- 数据依赖清晰
- 资源位置清晰
- 同步边界清晰

## 程序顺序与可观察顺序

PTO 程序中存在至少三种“顺序”：

### 文本顺序

程序中操作的书写顺序，是最直接的程序顺序。

### 数据依赖顺序

值的使用关系、buffer 读写关系和 view / tile 连接关系会形成数据依赖顺序。

### 同步顺序

某些操作即使文本上前后相邻，如果没有同步关系，也不一定意味着必须按完全串行方式执行；而一旦存在显式同步，就形成更强的顺序边界。

PTO 真正保证的是：

- 数据依赖不能被破坏
- 事件依赖不能被破坏
- 显式同步定义的架构可观察顺序不能被破坏

## 执行模型中的并行性

PTO 程序允许不同资源域、不同流水线和不同片上对象在依赖允许时并行推进。也正因为如此：

- 不能把所有 tile 操作都按普通串行算子理解
- 同步是执行模型的一等组成部分
- 内存副作用和地址空间会影响调度分析

结合 PTO 机器抽象，可以把并行性的来源概括为：

- 不同逻辑执行部件可以并行推进
- 不同局部存储域上的数据流可以交错展开
- 同步只在真正的依赖边界上建立，而不是默认全局串行

## 对程序编写的要求

从编程模型角度看，执行模型要求在程序中表达清楚：

- 哪些对象是真正的数据依赖
- 哪些对象只是逻辑别名或重解释关系
- 哪些阶段之间必须有显式同步
- 哪些函数或执行域标记运行在不同执行域

如果这些边界表达不清，后续的同步推导、内存规划和转换都会失去可靠基础。

从机器抽象角度再进一步看，还需要明确：

- tile 所属的逻辑存储域是否正确
- 数据搬运路径是否符合目标执行部件的消费方式
- 同步对象是否覆盖真实的生产者/消费者边界

如果这些约束不成立，程序即使语法上合法，也可能无法形成稳定的可编译执行模型。

## 执行模型与控制流

PTO 允许使用循环和分支（C++ 中即语言原生控制流，IR 中通过标准 dialect 表达），因此执行模型并不限于直线代码。循环和分支会进一步影响：

- 生命周期分析
- 同步推导
- tile 复用与内存布局

这也是为什么复杂控制流下，通常需要更保守的同步或内存策略。
